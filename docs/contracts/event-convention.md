# Event convention

Backs [ADR-0006](../adr/0006-event-idempotency-and-iam-role-conventions.md). Specifies the
envelope every event a blueprint's Lambda receives or emits carries, so "the shape of an event"
is a fixed, checkable set of fields rather than whatever the last producer happened to send.

## Envelope fields

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `eventId` | string (UUID) | Yes | Unique per logical event, assigned by the producer at creation. This is the field the [idempotency convention](./idempotency-convention.md) keys on — get this wrong and idempotency is wrong regardless of anything downstream. |
| `eventType` | string | Yes | A stable name, e.g. `order.refund_requested`. Determines the payload's shape. |
| `source` | string | Yes | Which producer emitted it, e.g. `orders-api`. Not a security boundary by itself — a consumer that trusts `source` without also verifying the channel it arrived on (a specific queue, a specific API key) has not actually restricted who can claim to be that source. |
| `occurredAt` | string (ISO-8601, UTC) | Yes | When the event happened, not when it was delivered — a redelivered event keeps its original `occurredAt`. |
| `schemaVersion` | string | Yes | The payload schema's version, e.g. `1`. A breaking payload change is a new `schemaVersion`, never a silent reshape of an existing one. |
| `correlationId` | string (UUID) | Recommended | Ties related events together across a workflow — the [orchestrated workflow](../blueprints/orchestrated-workflow.md) blueprint's execution history is the natural place this shows up, but any blueprint may set it. |
| `data` | object | Yes | The payload. Shape is free per `eventType`, versioned via `schemaVersion`. |

## Example

```json
{
  "eventId": "5e8b6e2a-6e33-4f9a-9c2e-2f6a1e9b6b3f",
  "eventType": "order.refund_requested",
  "source": "orders-api",
  "occurredAt": "2026-07-28T14:03:00Z",
  "schemaVersion": "1",
  "correlationId": "9d3c6a1e-8b2f-4e7a-9b1e-3f6a2e9b6b3f",
  "data": { "orderId": "ORD-7", "amount": 24.99 }
}
```

## Identity is assigned once, at the source

`eventId` is generated by the producer, at creation, and never regenerated by an intermediary —
not by the queue, not by a retry, not by a consumer that re-emits a derived event (a derived
event gets its own fresh `eventId`, carrying the original's id forward only via
`correlationId` if at all). A redelivery of the same event — SQS's at-least-once guarantee, a
retried Lambda invocation, a replayed EventBridge rule — carries the *same* `eventId` as the
original, because that identity is what makes a redelivery detectable as a redelivery rather
than a new event that happens to look similar.

## API Gateway is a special case: the client assigns the id

For the [synchronous API](../blueprints/synchronous-api.md) blueprint, there is no upstream
"producer" generating an `eventId` before the request arrives — the client is the producer. A
client that wants an idempotent write sends an `Idempotency-Key` header, and the handler treats
`Idempotency-Key` as that request's `eventId` for the purposes of the
[idempotency convention](./idempotency-convention.md). A client that omits the header has opted
out of idempotency protection for that specific call — the handler does not fabricate an id on
the client's behalf, because a fabricated id (say, a hash of the request body) treats two
distinct client intents that happen to have identical bodies as the same event, which is a
correctness bug in the other direction.

## Fields that do not apply

[Scheduled/batch](../blueprints/scheduled-batch.md)'s trigger is a schedule, not a message — the
EventBridge Scheduler invocation itself carries no meaningful `eventId` a producer assigned,
since there is no producer in the usual sense. That blueprint's idempotency concern (overlapping
runs, per the [idempotency convention](./idempotency-convention.md)) keys on the *run*, not on an
event envelope — see that document's own "fields that do not apply" note for the run-identity
shape it uses instead.
